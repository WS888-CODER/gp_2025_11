# Discrepancies and Issues — code vs. claims / architectural risks

Ranked roughly by how much they'd matter to a reader of the paper (most consequential first). Each item cites the exact file/line-level evidence found during this analysis; none of these are inferred from documentation or memory — all are directly observed in `functions/` or `lib/screens/`.

1. **[FIXED 2026-09-26] `cvAnalysisScore` (30% of the final score) was not computed from the candidate's CV.**
   Originally, `functions/interview/generateJobInterviewReport.js` never read the applicant's uploaded CV content; `ApplicationCVURL` was only passed through as a clickable link in the PDF, and `cvAnalysisScore` was scored purely from the interview transcript. **Fix applied, in two passes:**
   - *Pass 1:* the function now downloads the applicant's CV from `ApplicationCVURL` and extracts its text in-memory (`pdf-parse` for PDF, `mammoth` for DOCX — the same libraries `extractCVTextEnhancement` already uses elsewhere in this codebase, capped at 6000 characters), including it as a dedicated `Candidate's CV (extracted text)` block in the GPT-4 prompt. Falls back to answers-only scoring with a logged warning if CV extraction fails for a given application (corrupted file, unsupported format, download error, etc.).
   - *Pass 2 (design correction):* the first pass's wording told GPT-4 to score `cvAnalysisScore` from the CV "cross-checked against the interview answers," which reintroduced the same problem in miniature — it made `cvAnalysisScore` partially duplicate `jobRequirementsMatchScore` (which is specifically the interview-based requirements check) by blending interview evidence back into the CV score. Corrected so `cvAnalysisScore` is now CV-vs-job-posting **only**, with the interview transcript explicitly excluded by instruction. As a further consistency fix, `jobRequirementsMatchScore` (previously interview-answers-only) was widened to use CV + interview together, matching `requirementsChecklist` (which already used both) — the prompt now explicitly instructs the two to agree, since they evaluate the same requirements list against the same evidence and previously could have silently disagreed with no explanation visible in the report.

   This is a forward-looking fix only — it changes behavior for reports generated from now on; no past reports were regenerated or backfilled (none existed worth preserving at the time of this fix).

2. **[ACKNOWLEDGED, NOT FIXED — team decision 2026-09-26] SER-failure handling: excluded from grading, but displayed as 0 in the PDF.**
   In `generateJobInterviewReport.js`, the 10%-weighted `VoiceToneScore` **excludes** any answer whose SER call failed (`voiceScores.filter(s => s !== null)`) — this exclusion-from-weighting is intentional and correct. Separately, the PDF's per-question voice-tone section (`generatePDF`, inside the `for (const v of voiceAnalysisResults)` loop) computes `score = scoreMatch ? ... : "0.0"` — so a failed answer is still drawn in the report as a literal 0/100 with an empty bar, indistinguishable from an actual poor score. The team reviewed this and decided **not** to change it for now (low priority, not a real problem at this stage) — a low-effort future improvement would be a text label next to failed entries (e.g. "Voice analysis unavailable — excluded from score") instead of the bare "0.0", but this is left as-is by product decision, not because it was missed.

3. **The Speech-Emotion-Recognition (SER) internals (VAD, pause threshold, WavLM/eGeMAPS) are not in this repository and cannot be verified or cited from code.**
   The only artifact in this codebase is a Gradio client call (`Client.predict("predict_confidence", [audioBlob])`) to an externally-hosted Hugging Face Space (`wsaifaleslam/jadeer-smart-assessment`). No pause-length constant, VAD parameter, feature list, or hesitation-penalty formula exists anywhere under `functions/` or `lib/`. Any specific number for a pause threshold (0.6s, 1.0s, or otherwise) in the paper needs to be sourced from the Space's own implementation, which is outside this repository — it should not be presented as verified from "the code" reviewed here.

4. **`functions/jadeer-cv/` (the `extractCVKeywords` function that feeds the "For You" matching feature) is not wired into `firebase.json`.**
   `firebase.json`'s `functions.source` points only at `functions`; `functions/jadeer-cv` is a separate Node/TypeScript package with its own `package.json`, no `deploy` script, and no entry in `firebase.json`. It is plausible this is deployed via a separate manual step outside this repo, but that cannot be confirmed here. If it is *not* actually live, then `Users.CVKeywords` — and therefore the entire "For You" ranking on the job-seeker home screen — would silently never populate for CVs uploaded through the `cv/` Storage path. Worth confirming against the live Firebase console before writing "For You" up as a working feature.

5. **Login lockout (5 attempts/day) and account "Verified/Rejected" status changes are enforced entirely on the client, with no corresponding Firestore security rules found in this repository.**
   `lib/screens/login.dart` reads and writes `Users.failedLoginAttempts`, `accountLocked`, `mustResetPassword` directly via the Firestore client SDK; `lib/screens/admin_dashboard.dart` writes `Users.AccountStatus` the same way. This repository contains **no `firestore.rules` or `storage.rules` file at all**, and `firebase.json` has no `firestore`/`storage` config block, so it's impossible to confirm from code whether these fields are actually protected server-side from a modified/rooted client. If the paper's security section claims these are enforced "in the backend," that claim cannot be substantiated from this repository — rules would have to be pulled from the live Firebase console to check.

6. **Gmail credentials are hardcoded in plaintext in source.**
   `functions/index.js` lines 44–46:
   ```js
   const EMAIL_USER = "JadeerGp2025@gmail.com";
   const ADMIN_EMAIL = "walaasaif47@gmail.com";
   const EMAIL_APP_PASSWORD = "yfmitnbrrqwxfhvu";
   ```
   Unlike `OPENAI_API_KEY`/`HF_TOKEN`/`GOOGLE_TTS_API_KEY`, which are declared as Firebase Functions v2 `secrets` (Secret Manager–backed), the Gmail app password used for all outbound OTP/notification email is committed directly to the repository. This is a live credential exposure, not just a style issue, if this repository (or its git history) is ever made public or shared for the paper's reproducibility appendix.

7. **Two schedulers both close expired jobs, on different schedules, with different side effects.**
   `autoCloseExpiredJobs` (`functions/index.js`, daily at midnight Asia/Riyadh) sets `Jobs.JobStatus='Closed'` for jobs with `JobStatus=='Open' && EndDate<now`, with no notification. `closeExpiredJobsAndNotify` (`functions/notification/notifyJobStatus.js`, every 1 minute, UTC) does effectively the same status transition for `EndDate<=now` regardless of prior status, and additionally writes a `Notification` + sends an FCM push. Because `closeExpiredJobsAndNotify` runs every minute, it will almost always win the race and `autoCloseExpiredJobs` becomes dead code in practice — worth flagging as redundant/vestigial rather than describing both as intentional, distinct pipeline stages.

8. **`Applications.RecordExpiresAt` (`now + 120 days`) is written but never read.**
   Set once in `job_interview_service.dart` at interview creation. No function or query in this repository filters or acts on this field. The actual audio-retention rule enforced in code is unrelated: `deleteOldAnswerRecordings` deletes audio 2 days after `ReportGeneratedAt`. If the paper states a 120-day retention policy for interview recordings, that number describes an unused field, not the system's actual behavior.

9. **`deleteUserAccount` and `onJobDeleted` reference several Firestore collections (`CVEnhancement`, `Interview(s)`, `ReportGenerator`, `Reports`, `WebSchedule(s)`, `Favorites`, `Favourite`/`Favorite`, `AIServiceRequests`) that no other code in this repository writes to.**
   These appear only as delete-by-query targets. They may be legacy names from an earlier version of the app, collections written by tooling outside this repo, or simply unused defensive cleanup. Their presence should not be used as evidence that these features exist in the current system.

10. **The mock-interview `overallScore` has no explicit weighting formula, unlike the job-interview `Score`.**
    `functions/mockinterview/generateReport.js` asks GPT-4 to produce `overallScore` directly as one field of its JSON response; the acoustic voice-confidence score is given to GPT only as descriptive text in the prompt, with no code-level combination rule. If the paper describes "a 30/20/20/10/20 weighted score" as a property of Jadeer's interview reports generally, that formula applies to the **job interview** report only, not the mock interview report.

11. **Neither `gpt-4` report-generation call uses `response_format: json_object`, unlike the CV-enhancement and question-generation calls that do (for the JSON ones).**
    Both `generateJobInterviewReport.js` and `generateReport.js` (mock) rely on prompt instructions ("respond with valid JSON only, no markdown") plus manual ```-fence stripping and `JSON.parse`, which is a plausible (if usually reliable) source of runtime parse failures under the older `gpt-4` model. This is a code-quality observation, not a correctness bug that was observed to occur, but worth noting if the paper discusses reliability/robustness of the reporting pipeline.
